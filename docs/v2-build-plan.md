# Codoro v2 — build plan

v2 turns Codoro from a quiz app into a puzzle app. The flagship is the **execution scrubber** — stepping through code state and predicting what happens next — which the v1 retro identified as the actual fix for the quiz-vs-puzzle problem. The existing quiz modes stay and get upgraded, not replaced.

This plan absorbs `docs/v2-backlog.md`. Every backlog item is either assigned to a phase here or explicitly deferred to v3 — see the traceability table at the bottom. Nothing gets to hide.

## Locked decisions

Scrubber requires holding state and reasoning forward.                                                             |

Leaderboard, accounts, and the entire security block (Clerk, 2FA, rate limits, token storage) deferred to v3 | No marketing planned for v2 → a leaderboard is an empty room. | Trace ground truth | Scrubber traces are **derived by executing the code**, never asserted by an LLM                                                                 | v1's content weakness was unverifiable LLM assertions (ratings, explanations). ### OD-1 — swipe still unreliable on phone (third defect)

Phase 0 found and fixed two independent `@use-gesture` bugs (see the Phase 0 amendments: the 32ms `BEFORE_LAST_KINEMATICS_DELAY` staleness in `velocity`/`direction`, and `DragEngine`'s zero `axisThreshold.touch` silently locking the gesture to the wrong axis). A real-device pass on a preview deploy of the branch carrying **both** fixes still shows swipe problems, so this is a third, separate defect — not a regression of either fix, and not the stale-build case.

**Deliberately not diagnosed yet.** Phase 0 already spent two rounds on this, and the standing rule on this repo is no fix without a root cause read out of source. A third round of guesswork is worse value than deferring it behind Phase 1's routing work, which has to touch real-device PWA verification anyway. Two prior wrong diagnoses on this exact bug (the v1 retro's "`SwipeBinary.tsx` always resolves right", then the first `vx * dirX` hypothesis, which was right in effect but wrong in mechanism) are the reason.

**What must be captured before anyone writes code for this** — without it the next round is guesswork too:

- Device, OS version, browser, and whether it was the installed PWA or a browser tab
- Which failure it is, precisely: swipe does nothing (no commit), commits the wrong direction, commits when it shouldn't (accidental), fights vertical scroll, or card animates and then snaps back
- Whether it reproduces on a fresh page load vs. only after several puzzles
- Whether the tap fallback buttons still work when the gesture fails

**Candidate hypotheses, none verified — listed so the next session doesn't re-derive them, not as a shortlist to try:**

1. **PWA/service-worker cache.** Ruled unlikely (a preview deploy, not the installed app) but the installed PWA has its own cache lifetime; confirm the build hash on device before anything else.
2. **`touchAction: 'pan-y'` vs. iOS Safari.** The card allows vertical panning; iOS can hand a near-diagonal gesture to the scroller and cancel the pointer stream mid-gesture (`pointercancel`), which `@use-gesture` surfaces as a gesture that just ends. Related to but distinct from the axis-lock bug already fixed.
3. **The 20px `axisThreshold.touch` is now too generous** in the other direction — a short, fast, deliberate flick may not accumulate 20px before lift on a small screen, so the axis never locks and the drag never engages. This would be a tuning error introduced by the Phase 0 fix itself and is the first thing to test if the symptom is "short flicks do nothing, long drags work".
4. **`DEFAULT_SWIPE_THRESHOLD` (120px / 0.3 px/ms) is simply too high for a phone-width card.** Still last resort, same reasoning as Phase 0: don't retune to paper over a mechanism bug.
5. **framer-motion `x` spring fighting the drag transform** on lower-end Android — the card's own animation and the gesture writing to the same motion value.

**Not in scope for OD-1:** any redesign of the swipe interaction, and any change that lowers a threshold without a written mechanism for why the current value is wrong.

### OD-2 — `node:vm` is not a security boundary for JS trace generation

`jsTraceGen.ts`'s doc comment used to overstate this ("no require, process, fs, or timers are reachable from the sandboxed snippet"), which is true of the naive path but not a security claim `node:vm` actually backs — Node's own docs say so, and the Phase 2 corrective review confirmed the standard escape payload (`this.constructor.constructor('return process')()`) resolves the real host `process` object against this exact sandbox shape, not just in the abstract.

This is fine right now: Phase 2/3 snippets are hand-authored, so the threat model is "my own code," not "code I did not write." It stops being fine the moment Phase 4's batch pipeline runs LLM-generated snippets through this same generator unreviewed. **Not fixed here, deliberately** — the corrective PR that found this scoped the fix to enforcing determinism (Math.random/Date) and softening the doc comment to match reality, not to moving the JS backend to a child process (the Python backend already runs in a subprocess; JS does not). Phase 4 must decide, in writing, whether to isolate JS generation before its first batch run — this row stays open until that decision (and, if isolation is chosen, the commit implementing it) lands.

**Closed, Phase 4 — fixed by child-process isolation.** See the Phase 4 amendment below for the full decision record, including a residual finding from adversarial review (a blocklist of specific native-internals properties missed a hatch on the first pass; the shipped fix is a full allowlist instead) and why that isn't a full OS-level sandbox.

### OD-3 — output-checkpoint mask defeated by scrubbing backward

The Phase 3 pre-merge corrective (see that section's own amendment below) fixed a mask defeated by a co-valued row in the _same_ state panel. A fresh adversarial reviewer, running that corrective's mandatory revert-the-fix check, found a related but distinct hole while verifying the fix: masking is only computed while `stepIndex` exactly equals the pending checkpoint's `afterStep` (`isPendingAtStep` in `TraceRunner.tsx`). Backward scrubbing is unbounded — a player can always tap "Previous step" — so stepping back one from an `output` checkpoint's `afterStep` re-renders that earlier step with no masking applied at all. On `tc-009` checkpoint 1, `count` and `v` both hold `"3"` (the correct answer) one step before the pause, fully visible.

**`var-value` checkpoints are exposed to this too — an earlier draft of this row claimed otherwise, and that claim was wrong.** A Phase 2 corrective refinement requires a `var-value` target's own value to have changed since the previous step (`src/content/schema.ts`, "the masked value would already have been visible on screen before this question was asked"), which does guarantee the _target's own row_ differs one step back. But it says nothing about _sibling_ rows, and a sibling can independently hold the target's current-step value one step earlier. Confirmed live on `tc-009` checkpoint 0 (`var-value`, target `count`): at `afterStep` (step 6) `count` is `"1"`; one step back (step 5) `count` is `"0"` (correctly different, per the Phase 2 rule) but `v` is already `"1"` — the answer, sitting unmasked in a sibling row a full step before the pause. So both `var-value` and `output` checkpoints are exposed; `tc-009` alone confirms both (checkpoint 0 for `var-value`, checkpoint 1 for `output`).

**Not fixed in the Phase 3 corrective, deliberately.** Both candidate fixes are bigger than that corrective's scope: a UI-side fix means masking across a step range while a checkpoint is pending, not just at the exact pause (a real change to the gating/masking model, not an extension of the row-set it already computes); a content-side fix means a new validator rule (no variable, at any step from the checkpoint's `afterStep` back to the previous checkpoint or trace start, may equal the answer) — which, unlike the co-valued-row rule rejected for Finding 2, would not damage `mut-009`'s aliasing pedagogy, but would reject `tc-009` checkpoints 0 and 1 as currently authored and require content edits. Neither was a decision this corrective was scoped to make. Whoever picks this up next decides UI-side vs. content-side first, in writing, the same way Finding 2's alternatives were weighed — see that section's rejected-alternative reasoning for the standard to match — and should re-audit the full pool for this leak vector rather than assume `tc-009` is the only puzzle affected, since this row was written from the one adversarial pass that happened to hit it, not an exhaustive sweep. **Owner phase assigned as Phase 4 by the v2 Phase 1b corrective** (this row previously read "Undecided," the only field in the "Known open defects" table carrying no commitment) — the decision above is due before Phase 4's first batch generation run, same deadline OD-2 already carries: if the fix turns out to be content-side, the generator needs the rule before it produces 40–60 puzzles, not after.

**Closed, Phase 4 — fixed UI-side.** See the Phase 4 amendment below for the full decision record (why UI-side over content-side, the pool sweep's exhaustive-confirmation result, and the range-masking model itself).

### OD-4 — output-checkpoint answer leaks by containment, not just equality

Found during Phase 5 Item 0's full-pool sweep of `oob-011`'s two `output` checkpoints (the same sweep that found the distractor-format tell fixed in that item). OD-3's fix masks a visible variable's cell when its value is **equal** to the pending checkpoint's answer (`step.vars[name] === answerValue`). That catches the case OD-3 was built for — a sibling variable already holding the exact answer string — but an `output` checkpoint's answer is a whole printed line, e.g. `"initial window sum:" 9`, not a bare value. `windowSum` and `maxSum` both display `9` on screen at `oob-011`'s checkpoint 1 (`afterStep: 10`), and `9 !== '"initial window sum:" 9'`, so OD-3's equality check never fires — the value is visible anyway, embedded inside the printed line the player is being asked to identify.

This is a **containment** leak: the printed output _contains_ a currently-visible value rather than _equaling_ one. It is structurally distinct from the leak OD-3 closed, not a regression of that fix — `console.log("label:", x)` immediately after computing `x` is one of the most common shapes in this content, which means this is plausibly a systemic gap, not a one-off in `oob-011`.

**Not fixed here, deliberately** — Phase 5 Item 0's own instruction was to name this and give it an owner, not to fix it inline (a masking-model change is out of scope for a distractor-synthesis fix, and folding an unrelated UI change into that commit would make the revert-check review harder to reason about, not easier). Whoever picks this up should first run a full-pool sweep for this specific vector — this row was written from one confirmed case, not an exhaustive check — before deciding whether the fix is a substring-containment check in `TraceRunner.tsx`'s masking computation or something narrower. Assigned to **Phase 8**, alongside OD-1: the hardening/regression phase whose own DoD already requires every open defect-table row to be closed by a commit or carry a written waiver, rather than a content-pipeline or quiz-mode phase with unrelated primary scope.

**Amendment (code portions, post-implementation):** the swipe-direction skew,
validator, generator, and desktop-Browse items above matched the plan as
written — rebalanced 20/39 to "left" (48.7%/51.3% split), no schema change
surfaced, and the Browse fix stayed inside the existing `view` state machine
as expected. The gesture root cause is a refinement of this section's
hypothesis, not a contradiction, worth recording precisely: reading
`@use-gesture/core` v10.3.1's own source (not just its types) showed the bug
isn't really "`direction` reported from the last movement delta" in general —
it's that the library only recomputes `direction`/`velocity` on a gesture's
last frame when the gap since the previous frame exceeds an internal 32ms
threshold (`BEFORE_LAST_KINEMATICS_DELAY`), and recomputes from the delta
_since that gap started_, not the whole gesture. A finger that pauses before
lifting (common, and >32ms) makes that delta ~0, collapsing both fields
regardless of the drag's real distance/speed. Fix: `SwipeBinary.tsx` now
derives velocity from `movement`/`elapsedTime` (whole-gesture totals,
immune to any single frame's timing) via a new `signedVelocityFromGesture` in
`gestureThreshold.ts`, instead of `vx * dirX`. `DEFAULT_SWIPE_THRESHOLD` was
not retuned. Device verification (real iOS/Android feel) is still Thomas's,
per this section's original split of responsibilities.

**Amendment 2 (post-merge, real-device report):** after merging, real-phone
testing surfaced two further defects the above work didn't reach, both
confirmed by reading source/simulating before touching code (no fix without
root cause):

- **Gesture still dropped on phone.** A second, independent `@use-gesture`
  bug beyond the 32ms kinematics staleness fixed above: `DragEngine.ts`'s
  axis-intent lock (`axis: 'x'` in `SwipeBinary.tsx`'s `useDrag` config)
  defaults `axisThreshold` to `{ mouse: 0, touch: 0, pen: 8 }`. Zero tolerance
  for touch means the very first touchmove sample permanently locks the
  gesture's axis; real touchscreen jitter easily makes that first sample's
  vertical delta exceed its horizontal one, locking axis to `'y'` and then
  silently blocking every subsequent frame — including the final pointerup
  one — before it ever reaches the bound callback (`Engine.ts`'s `_blocked`
  emit-skip). The swipe just vanishes, with no error. This can't reproduce
  through a mouse or through the component test's mocked `useDrag` (both
  produce clean axis-dominant deltas), which is why it survived the previous
  fix and the full test suite. Fix: `axisThreshold: { touch: 20 }` added to
  the `useDrag` config, giving touch a few pixels of grace before locking the
  axis, matching the tolerance `@use-gesture` already gives `pen` by default.
- **Wrong-answer requeue starved fresh puzzles ("cycles through the same
  4").** Confirmed by simulating `src/engine/selection.ts` + `requeue.ts`
  directly: `selectNext`'s due-entry loop unconditionally preempts a fresh
  window pick whenever anything is due, with no bound on consecutive requeue
  serves. Missing a requeued puzzle again resets its ladder to a 3-tick
  countdown (`recordMiss`); once 3+ puzzles are cycling on that reset, at
  least one is due on literally every tick, so window picks never run again —
  the session gets permanently stuck replaying only the missed set. This also
  produced the reported "all swipes are left": a new user's rating-window
  puzzle set is small (5 swipe-binary puzzles within ±200 of the 1200
  starting rating, 4 of them "left" by chance), and getting caught in the
  starvation loop on that small, skewed set reads as "always left" even
  though the full library is a genuine 48.7%/51.3% split. Fix: `selectNext`
  gained a `lastSource` input — the caller's previous serve source — and now
  skips due-entry injection entirely when the previous serve was itself a
  requeue entry, bounding the requeue share of servings to at most every

This mattered more here than usual: Decision 1 above locked "don't record link attempts at all," so `puzzle_link_attempt` is the _only_ record link play ever happened — a double-fire corrupts the single signal the feature is evaluated by, the exact "feature is unevaluable" outcome instrumenting it was meant to prevent. 4. **Finding 4 (P0) — every real route was 3xx-redirecting to `/` on production, and it was a repo defect, not a dashboard one.** This **supersedes the wrong diagnosis** recorded in Item 0's amendment above. Elimination, all directly verified rather than assumed: 0 Page Rules; exactly one Redirect Rule active (WWW→apex, correct, doesn't match apex requests); production on the correct, successful `main` deploy; `codoro.pages.dev` (bypasses the `getcodoro.com` zone entirely) redirects identically, so the cause is inside the Pages deployment, not the zone; the deployment's own Redirects tab and build log confirm `_redirects` uploaded correctly ("Parsed 6 valid redirect rules"). Masked for anyone with the service worker already installed (it serves the cached shell without touching the network), which is why it went unnoticed and had to be tested in a fresh incognito window. Fixed by rewriting straight to `/` for all six routes and the `/puzzle/*` line this phase added (that line carried the identical defect, which would have shipped the same bug on the one surface whose entire value is a stranger opening a deep link cold). Did **not** switch to a `/* / 200` catch-all — that would destroy the deliberate "an unknown path returns a real 404" property `routes.test.ts` guards and Phase 1a documents. `routes.test.ts`'s `_redirects` drift guard and `DYNAMIC_ROUTES[].redirectsRule` updated to match the new `/` target.

**Standing lesson, worth carrying into every future phase:** this is the **second consecutive phase** (after the Phase 3 pre-merge corrective) where a defect survived a fully green test suite because the test's assertion was "does X appear," not "how many times does X happen." A `waitFor()` that stops at the first sighting of a UI state cannot distinguish "this happened once, correctly" from "this is still happening, over and over, after the assertion already passed." The specific shape to watch for: an effect that depends on a `useCallback` whose own dependency array includes state that callback itself updates is a render loop waiting to happen, and no amount of `waitFor`-based testing will catch it — only a count-based assertion, taken after a settling delay, will.

## Phase 2 — Scrubber spike: trace format, engine, tooling (2–3 sessions)

The risk phase. Everything unknown about v2 lives here: what a trace is, how prediction is scored, and whether trace generation can be automated. **UI polish is explicitly out of scope** — the deliverable is a proven format, engine support, and five end-to-end pilot puzzles rendered through a deliberately ugly debug harness.

**Build:**

1. **Trace schema** (in `src/content/schema.ts`, new `interaction: 'scrubber'` member of the discriminated union). Keep the trace minimal and flat:
   - `steps: Array<{ line: number; vars: Record<string, string>; output?: string }>` — one entry per executed line, variables as display strings (post-line state)
   - `checkpoints: Array<{ afterStep: number; question: 'next-line' | 'var-value' | 'output'; target?: string; choices: string[]; correct: number }>` — 2–4 pause points where the player predicts before the scrubber advances
   - Zod refinements: checkpoint answers must be consistent with the trace itself (e.g., a `var-value` checkpoint's correct choice must equal the trace's value at that step). **The schema mechanically rejects internally inconsistent puzzles** — this is the whole game for content quality.
2. **Trace generator tooling** (`src/content/tools/traceGen/`):
   - JS: instrument the snippet (babel transform inserting a per-line trace call) and execute in `node:vm` with a step budget and no I/O; capture line + locals per step.
   - Python: a `sys.settrace` harness run via subprocess, same output shape.
   - Output feeds the puzzle JSON directly. An LLM (or a human) writes the snippet and picks checkpoint locations; the machine writes the trace.
3. **Engine** (`src/engine/`): scoring for multi-checkpoint attempts. Locked rule: **all checkpoints correct on first try = solve; any miss = fail** — one binary rated outcome per puzzle, same as v1, so Elo semantics don't change. Per-checkpoint results are recorded in the attempt log for future partial-credit tuning, but rating stays binary in v2. Engine stays pure TS, lint boundary enforced.
4. **Five pilot puzzles**, at least two per language, authored end-to-end through the real tooling — not hand-written JSON. Rendered via a bare debug page (dev-only route).

- Does the flat trace model hold, or do the pilots immediately demand call stacks/objects/closures that break the schema?

If any answer is bad, renegotiate here — shrink checkpoint types, restrict to JS-only, or simplify the trace model — before UI and content spend.

1. **Authoring cost.** Not a clean under-15-minutes-flat answer. 3. **Does the flat trace model hold?** Yes, for what these 5 pilots needed — no pilot required a call stack, object graph, or anything the `steps`/`checkpoints` shape couldn't express. Two real, narrower limitations surfaced, both Python-specific and both worth naming for Phase 4's authoring guidance rather than treated as blockers:
   - A nested function's own frame doesn't expose the outer variables it closes over via `frame.f_locals()` (a CPython introspection fact, not a schema limitation) — `scl-010`'s checkpoints had to target the _outer_ scope's view of `i`/`vals` rather than "what does the lambda see internally," which happened to be exactly the right pedagogical angle for that puzzle, but would block a puzzle that specifically needs to show a captured value from inside the nested call itself.

Traces for structurally-equivalent JS/Python snippets are therefore not step-count-identical — expected, since each backend is faithful to its own language's real execution, and nothing in the schema assumes cross-language parity.

   None of these forced a schema change. **The flat model holds** for the pattern space these pilots targeted (loop state, aliasing, closures, truthiness); call-stack- or object-graph-shaped puzzles are simply out of scope until proven necessary, which the pilots didn't demand.

4. **Bundle bytes.** Measured directly, not estimated: built `dist/` twice from the same tree, once with the 5 pilot puzzle files present and once with them removed (all other Phase 2 code — schema, engine, generators — held constant, since that's real infrastructure cost the puzzles don't carry).

   - Both numbers land well under the "if pilots land above ~5 KB each, say so loudly" threshold from the locked-decisions table — no alarm here.
   - Extrapolated to Phase 4's 40–60 scrubber puzzle target, using the more conservative raw-JSON rate: **≈73–109 KB** of new puzzle content; using the measured bundled rate: **≈56–84 KB** actually added to `dist/`. That range is comparable to, and at the high end _exceeds_, the ~58 KB Phase 7 is separately trying to reclaim (per Phase 1a's amendment) — not a red flag on its own, but a real number Phase 7's performance budget should be planned against rather than discovered after the fact. Lazy-loading content per puzzle (ruled out this phase as premature at 5 puzzles, per the plan) becomes a more concrete candidate to revisit once Phase 4's volume is real.

**Net go/no-go: proceed to Phase 3.** No answer above is bad enough to renegotiate the format, shrink checkpoint types, or restrict to JS-only. The one concrete carry-forward for Phase 4: price the bundle-bytes number above into its volume/pipeline planning rather than re-deriving it, and expect (not fear) a similar tooling tax the first time batch generation hits a trace shape these 5 pilots didn't exercise.

This is now a documented standard, not a one-off fix: `src/content/README.md` states that any test asserting what a player actually sees at a checkpoint — a label, a masked value, a reveal string — must run against the real `scrubberPool`, with these two findings recorded as the worked example of why. `CheckpointPanel.pool.test.tsx` and `TraceRunner.pool.test.tsx` (both new) do exactly that for these two properties; the existing fixture-based tests were kept alongside, updated for the new prop/render shapes, as fast targeted regressions rather than replaced.

- **Note to Phase 4.** A co-valued `output` checkpoint is not an edge case the generator needs to avoid — it's the _ordinary_ shape of an output question, since `print(someVariable)` trivially co-varies the printed value with whatever variable held it. The validator does not, and must not, screen these out — see the rejected-alternative reasoning above. The mask-propagation fix in this amendment is what makes generating them at volume safe; do not reintroduce a co-valued-rejection rule when building the batch pipeline on the assumption the validator already screens for this.

- **Residual, deliberately not fixed here — tracked as OD-3** in "Known open defects" above: a fresh reviewer found that scrubbing _backward_ one step from a pending checkpoint re-renders that earlier step with no masking at all, since the fix above only computes masking exactly at the checkpoint's own step. This affects both directions, not just `output`: live on `tc-009` checkpoint 1 (`output`) and, via a sibling row rather than the target itself, also on `tc-009` checkpoint 0 (`var-value`) — the existing Phase 2 refinement only guarantees the _target's own_ row changed value one step back, it says nothing about siblings. Out of this corrective's scope — see OD-3 for the full mechanism and what a real fix needs to decide.

## Phase 4 amendment — pipeline build, pilot run, and a cost finding that changes the volume plan

Written personally, not delegated, per this phase's own instruction. Covers: the two-pass-becomes-three-pass correction to this phase's original spec, the sibling-module design call, the pattern allowlist, OD-2/OD-3's decision reasoning, the model-split call, and — the part that actually changes what happens next — real measured cost of `cli`-backend scrubber generation against the user's Claude subscription.

**1. This section's item 1 ("LLM proposes snippet + bug + checkpoint placements → trace generator executes → validator asserts") had a spec bug, corrected during the build, not followed as written.** Proposing checkpoint placements before a trace exists is impossible for anything but `next-line` — a `var-value`/`output` checkpoint's `choices` are real values at real executed steps, and those don't exist until the code has run. The pipeline (`generateScrubberPuzzles.ts`) is three passes: **propose** (model emits snippet + metadata only, no steps/checkpoints, against the new `ScrubberProposeSchema`) → **execute** (the trace generator — `jsTraceGen.ts`/`pyTraceGen.ts`, both child-process isolated per OD-2 below — produces `steps[]`, the only source of truth) → **place checkpoints** (a second model call, now holding the real trace, picks `afterStep`/`question`/`target` only). `traceGen/types.ts`'s doc comment ("`checkpoints` … is a human/LLM authoring decision, not something a trace tool derives from execution") is still true in fact — the trace tool still never decides — but the placement pass runs strictly after execution now, which the original one-pass wording didn't allow for.

Answer choices are never asked of the model at all, in any pass — `synthesizeChoices` derives `choices`/`correct` deterministically from the trace itself (a `var-value` target's other real historical values; other steps' real recorded output/state for `output`; other visited line numbers for `next-line`). This is cheaper, cannot fabricate an implausible-looking wrong answer, and is pedagogically the actual point: the best wrong answer to "what is `count` now" is a value `count` actually held earlier in this exact run. A checkpoint synthesis can't serve (e.g. a target that only ever held one value) is dropped, not patched with a model-invented fallback — if too few checkpoints survive, that attempt retries.

**2. Design call: sibling module (`generateScrubberPuzzles.ts`), not an extension of `generatePuzzles.ts`.** `generatePuzzles.ts` runs `main()` unconditionally at module import (its last line, before this phase, was a bare `main().catch(...)`) — anything importing it to reuse a helper would trigger a live quiz-generation run as an import side effect. The genuinely shared surface (id-counter logic, `writePuzzle`, cost/usage accounting, the calibration text) was extracted to a new side-effect-free `puzzleAuthoringShared.ts` that both files import; everything else (the manifest, the prompts, the generation shape) stays separate because it's genuinely different, not because of the import hazard. That import hazard turned out to be a real, not just theoretical, risk: building a unit test for `synthesizeChoices` that imported `generateScrubberPuzzles.ts` silently triggered a full `main()` run — including spawning the `claude` CLI — as a side effect of importing one pure function, caught only because the test took 57 seconds to "import" instead of milliseconds. Both this file and `generatePuzzles.ts` now guard their `main()` call behind an entrypoint check (`process.argv[1] === this file's own resolved path`); `generatePuzzles.ts` had the identical latent hazard even though nothing has ever imported it.

**3. Pattern allowlist — seven patterns, not all thirteen.** `off-by-one`, `mutable-state`, `scope-closures`, `type-coercion`, `control-flow`, `recursion-termination`, `data-structure-misuse`. Excluded, with reasons: **`concurrency` is unrepresentable in this format** — a trace is deterministic and single-threaded by construction (the trace generator's whole job is producing one canonical sequence of steps), so a race condition cannot be expressed as a trace at all; a "concurrency scrubber puzzle" would pass every machine check while teaching nothing, because there is nothing non-deterministic in the artifact for a player to reason about. **`null-undefined`, `input-validation`, and `error-handling` are typically one-step failures** — the bug manifests the instant a bad value is touched, with no interesting intermediate state to step through beforehand, which makes them fine quiz content (a `swipe-binary`/`mcq` question does the whole job in one shot) but poor scrubber content (there's nothing to trace). These four stay available to quiz generation; the allowlist is scrubber-only, enforced in `generateScrubberPuzzles.ts`'s manifest, not in the schema (a hand-authored scrubber puzzle outside the allowlist would still validate — this is a generation-time content-strategy decision, not a data-integrity rule).

**4. OD-2 (child-process isolation) — why isolation, not a narrower fix.** The alternative considered and rejected: patching the specific `node:vm` escape path found (`this.constructor.constructor('return process')()`) rather than moving execution to a new OS process. Rejected because `node:vm`'s isolation is explicitly not a security boundary per Node's own documentation — the confirmed payload is one instance of a general class of escape, not the only one, so patching it would just move the goalposts for the next adversarial pass. Isolation was already the established pattern for the Python backend (`pyTraceGen.ts` already shells out to `pyTracer.py` as a subprocess); this brings the JS backend to the same shape via a new `jsTracer.mjs` child process. Two measures beyond the OS-process boundary itself, found necessary by adversarial review during the build: the child's environment is allowlisted (`buildChildEnv` — `PATH`/`SystemRoot`/`TEMP`/`TMP` only; a naive `{...process.env}` would still carry the orchestrator's API key one process hop away instead of zero), and every own property of the child's real `process` object except the inert `exitCode` is deleted before any untrusted code runs — an **allowlist**, not a blocklist, because a first-pass blocklist of just `binding`/`dlopen` missed `process.getBuiltinModule`, an independent escape hatch to the same native capabilities. `jsTraceGen.ts`'s public signature and existing test suite are unchanged, per this phase's own constraint.

**5. OD-3 (backward-scrub mask leak) — why UI-side, not a content rule.** The alternative considered and rejected: a validator rule forbidding any variable, from a checkpoint's `afterStep` back to the previous checkpoint (or trace start), from ever equaling the pending answer. Rejected for three reasons, in order of weight: it would have rejected `tc-009` checkpoints 0 and 1 as already-authored content, meaning existing puzzles would need edits on top of the permanent-constraint cost; backward scrubbing is unbounded (a player can always scrub to step 0), so on a puzzle like `tc-009` (17 steps, 2 checkpoints) the rule would effectively have to hold across nearly the entire trace, which is a brutal generation filter that raises retry rate and cost while fighting the pattern-coverage targets; and it is structurally the same shape as the co-valued-row rule the Phase 3 pre-merge corrective already rejected for damaging `mut-009`'s deliberate aliasing pedagogy (`original`/`cart` being the same array by construction). The shipped fix instead masks the specific answer-valued cells (not whole rows, not whole steps) across the full range `[0, afterStep]` while a checkpoint is pending, computed from the checkpoint's own `afterStep` rather than the currently-displayed step — narrow enough that a player scrubbing back to re-read the trace can still read it. A full-pool sweep (not just the one adversarial hit that found the row) confirmed the leak was exactly `tc-009` checkpoints 0 and 1, 5 of 7 var-value/output checkpoints in the pool otherwise clean, before the fix landed. Revert-check test: `TraceRunner.od3.pool.test.tsx` against the real `scrubberPool`, fails on both cases if the range computation reverts to exact-`afterStep`-only.

**6. Model-split decision — resolved by live pilot evidence and a direct user call, not the plan's full formal measurement.** Decision 3 (locked) specified Haiku 4.5 generates, Sonnet 5 reviews, with an abort criterion: switch to Sonnet if Haiku's _semantic_ rejection rate (category 2 — well-formed content the schema/trace/review correctly reject, as distinct from category 1 backend parse failures) runs well above Sonnet's, measured via a same-spec re-run comparison. That full comparison was not completed. What happened instead: of the puzzles attempted under Haiku before the user intervened, multiple were discarded by Sonnet's review for real content defects — a checkpoint answerable by pure arithmetic without tracing execution, a systematic trace line-number mislabeling (every step tagged one source line earlier than the line whose effect it showed), and a factual arithmetic error in a generated explanation (claimed sum did not match the trace's own recorded output). None of these were backend parse failures — all were genuine category-2 rejections. On seeing this live, the user directed switching `GENERATE_MODEL` to Sonnet 5 mid-pilot rather than running the full comparison first. Puzzles generated under Sonnet afterward wrote successfully on the first attempt (no retries, no discards) for 2 of 3 attempts — consistent with, though far too small a sample to statistically confirm, the abort criterion's premise. **Recorded as a user decision, not a unilateral model call** — consistent with this phase's own "if ambiguous, stop and ask" instruction, just resolved faster, on real evidence, than the plan's own protocol would have. `GENERATE_MODEL` in `generateScrubberPuzzles.ts` is now `claude-sonnet-5`; the code comment at its declaration carries this same record.

**7. The actual cost finding — this is why the pilot stopped at 3 puzzles, not 10, and why stage 2/top-up are not scheduled.** Decision 4's premise was that the `cli` backend is "free" in the sense that matters for a user with no Console credits — it draws on Claude subscription usage rather than billing dollars. That premise is correct as stated, but **incomplete for planning purposes**: subscription usage is itself a finite, resetting quota, and this pilot consumed a materially large share of it for a small amount of finished content. Across two short runs (7 puzzle-generation attempts total, 3 written, 4 discarded — one run under Haiku, one under Sonnet after the switch), the user reported over a quarter of their Claude usage allowance consumed by generation activity alone, confirmed by direct observation during the run, not modeled from this file's token estimates. Two structural reasons the actual burn runs higher than `PROJECTED_TOKENS_PER_PUZZLE` in `generateScrubberPuzzles.ts` suggested: real Sonnet review-call output ran 3,000–20,000+ tokens per call in practice (the file's estimate was 250) — reviews apparently reason at length before returning `pass`/`reason`, which the estimate didn't anticipate — and the nested retry loop (this phase's own review-pass fix, item 4's commit) means a single stubborn puzzle can burn 10+ calls before either succeeding or exhausting its attempts, which is more resilient than discarding a good snippet outright but also spends more real usage per surviving puzzle than the flat 3-call estimate assumed. **This is the load-bearing finding for anything that generates scrubber content going forward**: the 40–60 puzzle target at this measured burn rate is not a single-session activity on a normal subscription allowance, and treating `cli`-backend generation as "cheap because it's not dollars" undersells its actual cost in the resource that's actually scarce. Any future stage (the plan's own "10 → stop → 30 → stop → top up" staging already assumed _some_ pacing; this finding says the pacing needs to be usage-window-aware, not just curation-time-aware) should budget by real measured tokens-per-surviving-puzzle from this pilot, re-run in small batches spread across usage-reset windows, and re-check the actual usage-consumed signal (not just the file's own projected numbers) after every batch, not only at the end.

**8. Re-derived cost basis.** `PROJECTED_COST_PER_PUZZLE`/`PROJECTED_TOKENS_PER_PUZZLE` in `generateScrubberPuzzles.ts` remain labeled estimates, not measurements, in the code — this amendment is the closest thing to a real measurement on record, and it says the estimate is materially low on output tokens per call (see item 7). Not corrected in code as a single new constant, deliberately: real Sonnet review-call length seemed to vary widely by puzzle (single-digit-thousands to 20,000+ output tokens) rather than clustering near one number, so replacing the current conservative-flat-estimate-plus-buffer with a single revised flat number would still be a guess, just a differently-wrong one. Whoever runs the next batch should pull real per-call numbers from this pilot's two run logs (both puzzle sets are on disk, `oob-010`/`011`/`012`, with full call-by-call usage lines in the terminal history) before trusting any projection, api- or cli-backend.

**Handback (Item 7 of this phase's build prompt), reported here since the pilot stopped short of the planned 10:**

- **3 puzzles live**: `oob-010` (off-by-one/Python/800-999, Haiku), `oob-011` (off-by-one/JS/1000-1199, Sonnet), `oob-012` (off-by-one/JS/1400-1599, Sonnet). All three passed the same `PuzzleSchema.safeParse` and self-review every other puzzle in the library passes — nothing here is exempted or hand-waved through.
- **4 discards**, all genuine review catches (zero were validator/schema failures — the mechanical layer did its job on every attempt): an answerable-without-tracing checkpoint (Haiku), a systematic trace line-mislabeling defect (Haiku), a factual arithmetic error in an explanation (Haiku), and an output-checkpoint distractor-format tell — two of four choices shared the correct answer's literal print-statement prefix, making the answer identifiable by format alone rather than by tracking state (Sonnet). Not fixed in this pass — flagged here per this phase's own "articulate a machine-checkable rule" instruction, since this one _is_ machine-checkable (compare each output choice's non-numeric/non-variable literal prefix against the correct answer's) and could become a `superRefine` rule or a `synthesizeChoices` change later.
- **Cost**: see item 7 above — the real story, not a dollar figure.
- **Recommendation**: do not schedule the 30-puzzle stage or a top-up run as a continuation of this session. Treat the next scrubber-generation batch as its own small, usage-window-aware activity, sized against real per-puzzle token numbers from this pilot rather than this file's original estimates, and re-verify actual usage consumption (not just the script's own running total) partway through rather than only at the end.

**2. Item 0 — root cause and why it reached production after being flagged.** The Phase 4 amendment's own handback (item 7) named this exact defect — an output-checkpoint distractor pool dominated by variable values, letting the correct answer's quoted print-label make it identifiable by format alone — and called it "a real, specific gap... worth a future fix," explicitly not fixed in that pass. Flat rather than compressing with the existing difficulty ramp (decision 5): the ramp already makes a harder puzzle take longer to read against the same clock, and compounding two untuned curves would make a miss untraceable to either one. **Timeout semantics, the actual design call here:** a puzzle timing out is treated exactly like a wrong tap — it consumes one of the existing 3 strikes via the same `handleAnswered` path, reaching the same ended phase through the same code, rather than opening a second, independent ending mechanism. `PuzzleCardShell` gained an optional `forcedCommit` prop for this — an externally-triggered commit that fires `onAnswered`/shows the locked feedback view exactly like a real tap, so Rush's clock never needed its own parallel "show feedback" path. The right-side progress bar shows the current puzzle's remaining time; strikes and difficulty already have their own indicators, so this is the one thing neither covers. `RUSH_STRIKE_LIMIT`'s and `RushPage.tsx`'s stale "no countdown timer" comments are corrected in the same commit, per decision 5's explicit instruction not to leave a stale locked-decision claim in source.
- **Trace's clock.** A per-checkpoint `TRACE_CHECKPOINT_TIME_LIMIT_MS` (30s, `TraceRunner.tsx`), not per-puzzle (decision 7) — a whole-puzzle budget would punish scrubbing, Trace's own core interaction, and one number can't fairly serve both a 3-checkpoint and a 4-checkpoint puzzle. It lives in `TraceRunnerPuzzle` (the component), not `useTraceSession` (the hook) — the hook has no concept of `stepIndex`, and "is a checkpoint on screen and unanswered right now" is a `stepIndex`-dependent question it structurally can't answer; `src/engine/` stays untouched either way. **The subtlest call in this item:** the clock pauses (not just stops) when the player scrubs away from the pending checkpoint, and resumes from wherever it was — not a fresh 30s — when they scrub back to that same still-pending checkpoint. A reset-on-return would let a player about to time out just scrub away and back for a free extension; this was worth getting right rather than shipping the simpler "always fresh on return" version. A checkpoint timeout produces `{ correct: false, choiceIndex: null }` — the exact `CheckpointResult` shape a real answer produces, no third state (decision 7's explicit requirement) — which required widening `CheckpointResultSchema`/`CheckpointResult.choiceIndex` to nullable (existing stored values are always real nonnegative ints, so this needed no migration of its own). `/puzzle/:id` renders Trace untimed (`timed={false}`) — a stranger on a link they didn't choose, already unrated, shouldn't also be timed.
- **Both clocks explicitly skip their own tick while `document.hidden`**, rather than relying on a browser throttling a backgrounded tab's `setInterval` — that's a performance behavior, not a correctness guarantee. This was caught, not assumed: a test that advanced fake timers past the limit while `document.hidden` was mocked true found the first version's clock fired anyway, since nothing in the tick callback itself checked visibility. A separate `visibilitychange` handler pushes the deadline forward once the tab (or, for Trace, the scrubbed-away step) becomes visible/active again.
- **The streak-pause moment (Item 7).** Fires at every multiple of 5 correct-in-a-row (5, 10, 15, ...), not just once at exactly 5 — a player who keeps choosing to continue keeps earning the moment. Practice and Trace only (decision 8): Rush is timed and interrupting a run is self-defeating, Daily is one puzzle so an in-session streak is undefined. The trigger rule (`resolveStreakPause`) is a small pure module (`streakPauseLogic.ts`) shared by both session hooks rather than duplicated — both need the identical rule, and this codebase has no other shared home for session-hook logic (the same reasoning `PuzzleCardShell.tsx`'s `assertNever` doc comment gives for not inventing a shared type-utils module). The UI (`StreakPause.tsx`) is a blocking, dimmed overlay per decision 8's own brief — the point of the feature is a place to stop, so it has to offer stopping as a real option: "Keep going" dismisses and serves the next puzzle immediately; "Done for now" only dismisses, leaving the already-committed puzzle's own feedback panel (with its own Continue button) visible underneath, so a player who wants to actually stop has a named way to do it rather than needing to intuit that ignoring the overlay is safe. Trace had no in-session streak counter before this item; one was added directly to `useTraceSession.ts` (increments on a solved puzzle, resets on a miss) since the trigger depends on it.
- **Payoff moments (Item 8).** Two, no more, per the brief. New-best-streak: when the pause fires at a streak exceeding the profile's stored `bestRunStreak` (a new field, persisted through the same profile update the rating/requeue write already makes — no separate save), the pause carries "New best streak" framing on the same screen, never a second interruption. New Rush personal best: the existing run-ended screen gains a "New personal best" line when `solvedCount` just beat the prior all-time `bestScore` — Rush is never interrupted mid-run, so the already-existing ended screen is the only legal surface, matching decision 8. **No rating-based celebration exists anywhere in this diff** — deliberately: the stored rating is still inflated by pre-rebalance blind-right swipes (Phase 0's reset note), so a "new peak rating" moment would be celebrating an artifact, not a real achievement.
- **Storage.** `CURRENT_SCHEMA_VERSION` 4 → 5, one migration (`migrateV4ToV5`) doing two small things rather than two sequential version bumps, since both ship in the same PR: `rushStats` resets to `null` outright (decision 1 — the existing bestScore/bestStreak were earned untimed and aren't comparable once a clock exists; there's no real player data to preserve, so reset rather than build a dual-key untimed/timed split), and `bestRunStreak` is added at `0` for every existing profile.
- **Telemetry, additive only.** `timed_out` on Rush/Trace per-attempt events; `ended_reason` (`'strikes' | 'clock'`) and `is_new_best_score` on `rush_run_end`; a new `streak_pause` event (`mode`, `streak`, `is_new_best`). None of the locked `attempt` schema's existing fields were renamed or restructured. Documented in `telemetry/README.md`.
- **A filename collision, worth recording since it'll recur if this pattern (a component + its own pure-logic module, same base name) comes up again:** `streakPause.ts` (the logic module, lowercase-first per this codebase's existing module convention) and `StreakPause.tsx` (the component, PascalCase per this codebase's existing component convention) differ only in their first letter's case. Windows and default macOS filesystems are case-insensitive, so this built and ran locally without incident — but `tsc` itself flags it as a hard error (`TS1149`), because a case-_sensitive_ filesystem (any standard Linux CI runner) could resolve the two import paths inconsistently depending on which one a given build happens to touch first. Renamed the logic module to `streakPauseLogic.ts` rather than renaming the component off its established convention.
- **Process note.** Items 6–8 were substantially larger in combination than Item 5 alone, and were implemented and reviewed directly by the lead in one continued session rather than delegated to fresh subagents per item, given the mid-task pivot from "stop here" to "continue through the rest" — the addendum's own leaner-review allowance ("mechanical commits... don't get their own reviewer") was extended further than originally scoped, in the interest of finishing the phase in one coherent pass rather than fragmenting review across many small hand-offs. Each item was still typechecked, linted, tested (827 → 843 → 861 tests across the three commits), and validated end to end before committing.

- **Data shape.** `DragOrderSchema` (`content/schema.ts`) adds `blocks: string[]` (the shuffled, on-load display order — never the correct order) and `correct_order: number[]` (a permutation: `correct_order[i]` is the `blocks` index belonging at position `i`), minimum 3 blocks, validated as a real permutation (right length, no duplicates, no gaps). A same-pass schema addition rejects the identity permutation outright — a drag-order puzzle whose blocks are already correctly ordered on load isn't a puzzle, and nothing upstream (hand-authored content, `generatePuzzles.ts`) was already guarding against a generator producing exactly that.
- **Rush exclusion.** `drag-order` joins `scrubber` as the second interaction type Rush's speed format deliberately never serves — a multi-block drag gesture doesn't fit a countdown-pressure format the way a single tap/swipe/mcq answer does. `RushInteraction` (`engine/rush.ts`) stays `'mcq' | 'swipe-binary' | 'tap-line'`; enforcement is `useRushSession.ts`'s existing hand-written `isRushEligible` type predicate, now backed by a runtime regression fixture (`useRushSession.test.ts`) that serves 12 attempts against a pool salted with drag-order puzzles and asserts none are ever served — a predicate's body isn't checked against its asserted type by the compiler, so this is the only thing that would actually catch a future accidental widening.
- **Drag model.** Native Pointer Events only, no gesture-library dependency (unlike SwipeBinary's `@use-gesture/react`) — `setPointerCapture`/`releasePointerCapture`, a pure swap-threshold helper (`dragOrderReorder.ts`'s `resolveDragSwap`, mirroring `gestureThreshold.ts`'s established split of pure gesture math from the component) driving a swap-based reorder. Rows render in fixed DOM order by block index and are repositioned purely via `transform: translateY(...)` — nothing ever reflows mid-drag.
- **Two real-device bugs an independent review caught that no automated test in this environment could have (jsdom has no real layout or touch semantics), both fixed pre-merge:** `touch-action` toggled inside the pointerdown handler was already too late — a browser decides whether a touch starts native scroll or a custom gesture at hit-test time, before any JS handler runs — fixed by moving `touch-action: none` to a static CSS rule scoped to a dedicated `.drag-order__handle` child, not the whole row. And the transform math used `getBoundingClientRect().height` alone for row spacing, silently ignoring the list's CSS `gap` — positions would drift by the gap's width per displaced slot on any real render. Fixed by measuring real top-to-top slot pitch (`resolveSlotPitch`) instead of height alone.
- **Also fixed in the same pass:** a redundant `finalOrder` state variable (the `order` state already holds the final arrangement once locked); `DragOrder`'s internal state not resetting when `puzzle.id` changes without a remount (breaking `PuzzleCardShell`'s own documented no-`key`-needed guarantee); a keyboard fallback (arrow keys move the focused block) for players without a pointer; and three hand-authored fixture puzzles' provenance (not pipeline output) now noted in `content/README.md`.
- **Process note:** the fix round for the review's findings was interrupted mid-edit by an account-level session-limit block. Its in-progress, uncommitted changes were inspected file-by-file rather than discarded or re-run from scratch — they turned out complete and correct for every file the round had reached, but two test files (`DragOrder.test.tsx`, `content/schema.test.ts`) it hadn't yet reached were left asserting against the pre-fix component/schema shape (wrong pointer-event target, a stale mock, and a default fixture using the now-rejected identity permutation). Those two were finished directly rather than re-dispatched, given the same usage-budget instruction driving this PR's scope. `pnpm validate` (typecheck, lint, full test suite, content validation, build) is green.
- **Post-merge-attempt correction: the "top-to-top slot pitch" fix above (a single shared measurement) was itself still wrong, caught by the user actually dragging real content on merge.** `blocks` are prose under `white-space: pre-wrap`, and real content already has blocks 15+ characters apart in length (`rec-009.json`'s range ~31–47 chars) — on a real phone width, some blocks wrap to two lines and others don't, so treating every row as one uniform height/pitch (the fix directly above) drifts exactly as much as ignoring the gap did. Replaced with a genuinely per-row model (`dragOrderReorder.ts`'s `RowLayout`/`computeRestTops`/`computeTranslateYs`/`restCenterAt`): each block's own measured height feeds a cumulative rest-position sum, and the drag gesture tracks the dragged row's live absolute center (rest center at gesture start plus total pointer movement) rather than adjusting a relative offset per swap — the latter doesn't generalize once neighbors can have different heights. This also fully resolves a keyboard-reorder bug an automated PR reviewer (Copilot) separately flagged (arrow-key moves before any drag left the transform multiplied by an unset zero pitch): the new model measures layout once per puzzle via a mount effect rather than lazily on first interaction, so there's no first-interaction-type ordering to get wrong. Separately, that same automated reviewer's own autofix (changing a test's `correct_order` off the now-rejected identity permutation) fixed the schema-validity problem but broke the test's actual expectation — worth flagging as a general caution about autofixes that satisfy a linter/type-checker without re-deriving the test's real intent.

## Phase 5c — Challenge links (1–2 sessions, added 2026-08, runs immediately after 5b merges)

todo.md item 2, pulled forward by direct user decision: challenge links are v5.0's async duel minus accounts and minus a server, buildable now, and the only distribution channel Codoro has before v3 — a friend receiving a challenge link is the first stranger-adjacent user the product gets. **The no-backend lock holds**: the entire challenge lives in the URL.

**Build:**

1. **Challenge payload, versioned and URL-encoded.** Compact JSON → base64url: `{ v: 1, ids: string[], results: per-puzzle correct/time, totalMs }`, capped at ~5 puzzle ids so the encoded URL stays well under the ~2K practical length limit. A malformed, truncated, or unknown-version payload renders a legible "this challenge link is broken" state, not a crash — same standard as `/puzzle/:id`'s bad-id branch. **Forgeability is accepted, in writing**: with no server there is no integrity check; a friend who hand-edits a URL to claim a perfect run is a social problem at friend scale, not an engineering one. Do not add crypto to a party trick.
2. **Route + serving.** `/challenge` (payload in query or fragment — decide and record; a fragment never reaches Cloudflare or the SW, which simplifies both). Whatever the choice, run the full Phase 1a/1b routing checklist: `_redirects` entry, SW `navigateFallbackDenylist`, `routes.test.ts` drift guards, `DYNAMIC_ROUTES` if pathful — and the Finding 4 lesson: verify a cold load on production **in a fresh incognito window**, not through an installed SW's cache.
3. **Flow.** Challenger finishes a Practice streak / Rush run / Daily solve → "Challenge a friend" affordance → link encodes their result. Recipient opens the link, plays the same puzzles in sequence, then a comparison screen (you 4/5 in 63s vs. their 5/5 in 48s) with two CTAs: counter-challenge (re-encode with your result) and "practice more like this". Serves from `puzzlePool` (full union — same reasoning as `/puzzle/:id`; a scrubber puzzle in a challenge is fine, the comparison is per-puzzle correct/time either way).
4. **Unrated, structurally.** Same as Phase 1b's Decision 1: challenge attempts are never recorded to the attempt log or profile — "never rated" stays structurally true rather than switch-case true. Telemetry is therefore the only record: `challenge_create` (`{ surface, puzzle_count }`), `challenge_link_view` (`{ found }`), `challenge_link_complete` (`{ beat_challenger }`) — additive, snake_case, `src/telemetry/README.md` updated in the same commit.
5. **OG stays option (a)** (generic card). Note for the record: (b1) build-time prerendering can never cover challenge URLs — the payload is dynamic — so the generic card is permanent for this surface until a v3 edge function exists. Acceptable; the link's pitch is the message text around it, not the unfurl.

**DoD:**

- [ ] Payload round-trips encode→decode with a versioned schema and tests; tampered/truncated/unknown-version payloads produce the legible broken-link state
- [ ] Cold load of a real challenge link on production renders the challenge (verified incognito, per Finding 4)
- [ ] Challenge attempts never touch the attempt log or profile — asserted at the storage layer, same standard as `/puzzle/:id`'s test
- [ ] Comparison screen renders both results and both CTAs; counter-challenge produces a valid link
- [ ] All three telemetry events land in PostHog from production (depends on the Phase 0 PostHog verification actually being done)
- [ ] `pnpm validate` green; zero new dependencies
