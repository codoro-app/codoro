# Codoro v2 "Arena" Design System Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace Codoro's current (Phase 6.5) light/dark "chess.com-ish" token system and component chrome with the v2 "Arena" dark-only design system defined in `docs/design/codoro-v2-arena.html`, screen by screen, in the exact commit order the source brief specifies, without regressing any existing behavior, test, or gesture logic.

**Architecture:** Nine sequential commits on a new branch `ui-v2-arena` off `main` (which already includes Phase 6.5 + the mastery-panel-sync fix — verified below). Each commit is independently revertable: fonts → tokens → shell/nav → puzzle/code/feedback → browse → mastery → daily/share → pwa cleanup → grep-proof + screenshot QA + PR. `docs/design/codoro-v2-arena.html` is the literal source of truth for every color/spacing/radius decision below; it is a design-canvas export (inline styles, `sc-camel-view-box` typos, placeholder puzzle content) and must never be copied into component markup — only its _visual decisions_ are ported.

**Tech Stack:** React 19 + Vite 8 + vite-plugin-pwa (Workbox) + Vitest. No CSS framework — hand-written per-feature `.css` files consuming `src/index.css` custom properties. No new npm dependencies permitted (house rule).

## Global Constraints

- Zero hex color literals outside `src/index.css` (existing rule, currently holds — verify it still holds after this work with the grep proof in Task 9).
- No emoji used as UI iconography anywhere the v2 design replaces it (exception: `src/app/pwa/**` is explicitly out of scope — see below).
- `src/app/pwa/` stays hands-off. Renaming CSS custom-property _names_ referenced inside `pwa.css` (mechanical find/replace, e.g. `var(--text-muted)` → `var(--text-1)`) is in scope. Any other change in `src/app/pwa/` (new visual treatment, emoji removal, layout changes) is **out of scope** — list every touched line under `pwa/` explicitly in the final summary even if it was "just" a token rename.
- No changes to `SwipeBinary.tsx`'s or `gestureThreshold.ts`'s drag/threshold logic — CSS/className changes only.
- No changes to rating math, telemetry, streak logic, share-text generation (`shareText.ts`), or OG image generation.
- All existing tap targets stay ≥44px (`--tap-target-min`), all existing `aria-*`/`role` attributes are preserved.
- `pnpm validate` (typecheck + lint + test + content-validate + build) must be green before the final PR.
- Every commit is a normal commit on `ui-v2-arena` — no `--no-verify`, no amending.

### 3. Elevation: box-shadow chrome is retired

The Phase 6.5 rule ("box-shadow is allowed for chrome regions — nav rail, right-panel sidebar — via `--shadow-card`") does not survive into v2. The reference's `<nav>` rail has `border-right: 1px solid var(--bd)` and no background/shadow at all (transparent, inherits the page's `--bg0`); the reference's `<aside>` sidebar has `border-left: 1px solid var(--bd)` and likewise no background/shadow. Delete `--shadow-card` from the token file and remove every `box-shadow: var(--shadow-card)` usage. Concretely (Task 3):

- `.nav-rail` (`app.css`): drop `background: var(--surface-raised)` and `box-shadow: var(--shadow-card)`; keep `border-right: 1px solid var(--border)`.
- `.practice-page__sidebar, .daily-page__sidebar` (`practicePage.css`): drop `background`, `box-shadow`, `border-radius`; add `border-left: 1px solid var(--border)`.

### 4. Spacing scale — keep the existing token names/values

The reference file's paddings/gaps (60,44,42,34,30,24,22,20,18,17,16,14,13,12,11,10,9,8,7,6,5,4px) are a hand-tuned canvas export, not a strict grid — many values (13,15,17,18,19,22px) don't land on any sane 4px-based scale. Keep `--space-1` through `--space-8` exactly as they are today (they already cover 4/8/12/16/20/24/32px, which is most of the design's rhythm). Where a specific component genuinely needs an in-between value (e.g. an 18px panel padding), use that literal pixel value directly in the component's own CSS rule — this is normal, doesn't violate "zero hex outside index.css" (that rule is about _colors_), and avoids bloating the token file with one-off spacing values nothing else reuses.

### 5. Radius scale — new 6-step scale, grounded in observed clusters

```css
--radius-xs: 6px; /* tiny chips/badges: MCQ letter chips (A/B/C/D), SOON tag */
--radius-sm: 10px; /* nav items, tabs, small interactive rows */
--radius-md: 12px; /* buttons, code surface, cards, MCQ choices, browse tiles — unchanged from current value */
--radius-lg: 16px; /* mastery panel card, share card */
--radius-xl: 18px; /* hero result card (Daily solved panel) */
--radius-full: 999px; /* pills, circular swipe buttons */
```

Pixel-perfection is not required per the DoD — this collapses ~15 observed radius values into 6 reusable buckets by nearest cluster.

### 6. Buttons lose the Duolingo "3D press-lip" treatment

The reference's primary CTA buttons ("Next puzzle", "Continue", "Copy share text", "Practice all") are flat: `border:none`, no `border-bottom` lip, no `:active` translate. This is structurally incompatible with `--primary-action-border` (the lip color), which is why that token is deleted. Replace `.feedback-panel__continue:active` / `.update-prompt__refresh:active` / `.share-card__button`'s lip mechanic with a lightweight pressed state instead — the DoD explicitly calls out that hover/pressed/focus-visible states aren't in the static mock and must be derived from the token system:

```css
/* replaces the border-bottom-lip mechanic everywhere it currently appears
   in practice.css, pwa.css, dailyPage.css (except pwa.css — token-rename only there) */
.feedback-panel__continue {
  border: none;
  transition:
    transform 0.05s ease-out,
    opacity 0.05s ease-out;
}
.feedback-panel__continue:active {
  transform: scale(0.98);
  opacity: 0.9;
}
.feedback-panel__continue:focus-visible {
  outline: 2px solid var(--accent);
  outline-offset: 2px;
}
```

Apply the same three-rule pattern (flat border, `:active` scale+opacity, `:focus-visible` accent outline) to every primary CTA in scope: `.feedback-panel__continue`, `.share-card__button`, `.pattern-picker__all`/"Practice all patterns" button. `pwa.css`'s `.update-prompt__refresh` keeps its existing lip mechanic (out of scope — token renames only there, per the Known Issue rule).

### 7. StatusBar pills lose the solid-accent-background pattern

`--pill-text` is deleted because the pattern it served (colored text on solid-accent/warning pill background) doesn't appear in v2. The reference's stat chips are `background: var(--bg1); border: 1px solid var(--bd)` with a colored SVG icon and `--text-0`-colored value text — see Task 3 for the exact replacement markup (SVG icons replace 🏆/🔥, conditional coloring on the streak icon).

### 8. Layout width tokens — recomputed from the reference's desktop frame

- `--nav-rail-width`: `240px` → **`220px`** (reference nav rail is exactly 220px wide).
- `--sidebar-width`: `320px` → **`296px`** (reference aside is exactly 296px wide).
- `--content-width-desktop`: `720px` → **`640px`** (reference desktop frame is 1240px; minus 220px rail, minus 296px aside, minus the main column's own 42px×2 horizontal padding = 640px usable content width).
- `--content-width-mobile`: `480px` — **unchanged**, no reference evidence to correct it (no tablet-width mock exists).
- `--tap-target-min`: `44px` — **unchanged** (accessibility floor, not a design-file value).

### 9. Syntax highlighting: drop italic comments

Current `.token.comment` sets `font-style: italic`. No comment token appears in any reference code snippet with italics — drop `font-style: italic`, color only (`--syn-cm`).

### 10. Mastery/browse accuracy-state thresholds (derived from the four data points shown across 2d/2l/2m)

| State    | Accuracy            | Badge/fill color                                           | Row/card treatment                                                                                                                         |
| -------- | ------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| No data  | `accuracy === null` | `--text-2`, no pill background                             | plain, muted — matches existing "Not enough data (x/y)" copy, just not pill-wrapped                                                        |
| Mastered | `>= 0.8`            | `--accent` text on `--accent-dim` pill bg, fill `--accent` | normal row                                                                                                                                 |
| Learning | `0.4 – 0.79`        | `--warn` text on `--warn-dim` pill bg, fill `--warn`       | normal row                                                                                                                                 |
| Weak     | `< 0.4`             | `--danger` text, fill `--danger`                           | **row background `--danger-dim`, border `--danger`** (only state that recolors the whole row, matches 2m's "Concurrency · weak" treatment) |

Verified against reference: 92%/88% → accent, 71%/63%/64% → warn, 38% → danger+highlighted row, `null` → muted no-pill. `MIN_ATTEMPTS_FOR_MASTERY` and the existing "Not enough data (x/y)" copy stay unchanged — only the visual treatment changes.

### 11. Browse patterns needs mastery data it doesn't currently have

`PatternPicker.tsx` today is presentation-only (pattern name + navigate on click) — it has no accuracy/progress data. The v2 Browse screens (2d/2i) show an accuracy badge + progress bar + state caption ("5/5 · mastered") per pattern card. `MasteryView.tsx` already computes exactly this via `computeMastery(attempts, puzzlePool)` (from `./mastery`). **Decision: wire `PatternPicker` to call the same `computeMastery`/`listAttempts` it already uses elsewhere** (Task 5) — this reuses an existing pure function and existing storage read, it does not introduce new business logic, and without it Browse cannot "read as the same design" per the DoD (a bare list of names is a materially different, degraded screen vs. the reference). This is flagged here explicitly rather than silently added — if you disagree with this scope call, stop before Task 5 and say so; the fallback is a style-only Browse list with no accuracy badges, listed as a gap in the final summary instead.
