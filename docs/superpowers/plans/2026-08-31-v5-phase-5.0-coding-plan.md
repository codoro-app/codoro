### Session 2 — the API can tell who you are and how often you may ask

**T3 — auth middleware.** JWKS-based Clerk session-token verification on every authenticated route, networkless via the pinned `CLERK_JWT_KEY`. Explicit 401 (no/!valid token) vs 403 (valid token, not your row) split. Forged, expired and `aud`-mismatched tokens each get a test. `@clerk/backend` v3 in the Worker, paired with `@clerk/react` v6 in the client at T5 — do not mix a Core 2 client with a Core 3 backend.

The authorization helper is separate from the authentication middleware and is the only thing that answers "may they do this" (I5). Nothing reads a role, capability or flag from the request body (I9).

**T4 — rate limiting.** Cloudflare's `ratelimits` binding (GA, no additional charge, config in `wrangler.jsonc`, `namespace_id` self-chosen, Wrangler ≥ 4.36.0). Not the legacy `unsafe` form. Limits live in `workers/src/limits.ts` as a route → `{perIp, perUser}` table — config, not magic numbers.

Two properties the binding does **not** have, and which the tests must encode rather than paper over: the window is only 10 or 60 seconds, and counters are **per Cloudflare location**, not global. So the binding does burst damping; every _exact_ quota is enforced in D1 where the constraint already lives. Write the test that proves the D1-enforced quotas hold with the limiter disabled — they must not be co-dependent.

**T4a — `POST /api/report` (new task; the build plan's 5.0 item 5 had no task).** Roughly an hour on top of the foundation, and it does not get to grow.

- Unauthenticated **by design** — guest-first is law and most reporters will not have accounts. That makes it the only anonymous write in the system and therefore its sharpest abuse surface.
- Body: `{ puzzleId, reason, appVersion }`. `reason` is validated against the fixed enum by Zod **and** by the table's CHECK constraint. `puzzleId` is validated against the real content metadata index — import the `puzzleMeta` module #82 created, do not duplicate it. **No free-text field reaches storage, in any form.**
- Strict per-IP rate limiting. No PII stored, no IP column hashed or otherwise.
- No moderation UI, no admin read endpoint, no `clerk_user_id` column "for later". Those are v6 decisions with a surface attached.

**DoD for the pair:** auth middleware rejects forged/expired/mismatched tokens (tested); authz helper enforces row ownership (tested); limiter burst test returns 429 with `Retry-After`, per-user and per-IP keys independently tested; `/api/report` accepts a signed-out report, rejects an unknown puzzle id and an out-of-enum reason, is per-IP limited, and stores no PII.

**Versions actually installed (F7):** `@cloudflare/vitest-pool-workers` **0.22.0** (matches the plan's estimate) · Hono **4.13.7** · Wrangler **4.130.0** (already installed, ≥ 4.36.0 satisfied) · `@cloudflare/workers-types` **5.20260908.1**, deliberately pinned to the exact version already used at repo root rather than letting it float independently (see the footgun below) · TypeScript `~6.0.2` (matches root).

**Platform-surface change found at install, not in the plan (F7):** `@cloudflare/vitest-pool-workers` 0.22.0 targets Vitest 4's Test Projects API. There is no `@cloudflare/vitest-pool-workers/config` export and no `defineWorkersConfig()` — the plan's Vitest-3-era shape. The current shape is a Vite plugin: `import { cloudflareTest } from '@cloudflare/vitest-pool-workers'`, used as `plugins: [cloudflareTest({ wrangler: {...} })]` inside a plain `defineConfig()`. The `wrangler: { configPath, environment }` option shape itself is unchanged. Separately, `cloudflare:test`'s `env`/`SELF` exports are marked deprecated in favor of `cloudflare:workers`'s `env` (which resolves against the global `Cloudflare.Env` — the same augmentation point `wrangler types` would generate); `workers/test/health.test.ts` uses the new import.

**`workers/src/env.d.ts` hand-maintains the `Cloudflare.Env` augmentation instead of running `wrangler types`.** Tried `wrangler types --env dev` first — it works, but bakes the _dev_ env's literal values (`ENVIRONMENT: "dev"`, `CLERK_INSTANCE: "development"`) into the generated `Env` type, which is wrong for a type meant to describe both `dev` and `production`, and needs a manual rerun after every `wrangler.jsonc` edit (its own footgun, adjacent to F6). Hand-writing the augmentation once, kept in sync with wrangler.jsonc's binding names by convention, avoided both problems — at the cost of one real bug caught by `tsc`: `declare namespace Cloudflare { interface Env extends Env {} }` resolves the inner `Env` to `Cloudflare.Env` itself (namespace-scoped lookup shadows the module-scope name), silently merging in _nothing_. Fixed with a distinctly-named base interface (`WorkerEnv`), the same indirection `wrangler types`'s own generator uses under a different name.

**Rate limiter numbers are explicit placeholders, not silently picked.** `wrangler.jsonc`'s `ratelimits` binding requires a `simple: {limit, period}` value to exist at all — there's no way to declare "the binding exists, policy TBD" the way there is for, say, an unset var. Both bindings ship as `{ limit: 100, period: 60 }`, commented as T4's to finalize; nothing in `/api/health` (T1's only route) ever calls `.limit()`, so the placeholder has zero behavioral effect yet.

**`CLERK_INSTANCE` added as a var** (`dev` → `"development"`, `production` → `"production"`) so `/api/health`'s `clerkInstance` field — the prompt's explicit ask, "F1's one-curl diagnostic" — means something before T3 wires real Clerk-key verification. It's a label today, not a cryptographic check; commented as such.

**`compatibility_date` pinned to `2026-08-01`, not `2026-09-08`.** The installed `@cloudflare/vitest-pool-workers` bundles its own `workerd`/Miniflare build (`miniflare@5.20260815.0-alpha`), which refused to start local tests against `2026-09-08`: _"newest date supported by this server binary is 2026-08-22."_ Picked a date safely under that ceiling. This governs the **locally-tested and actually-deployed** Worker; bump it only after confirming the installed `vitest-pool-workers`'s ceiling has moved too, or `pnpm validate` breaks on a fresh clone (F5).

**`VERSION` is not a static wrangler var.** CI's deploy job passes it at deploy time (`wrangler deploy --env dev --var VERSION:${{ github.sha }}`) so `/api/health` reports the exact live commit; local `wrangler dev` and an unset-VERSION deploy fall back to the literal `"dev"`.

**Real footgun found and fixed during this task: mismatched `@cloudflare/workers-types` versions blew up `pnpm lint` from ~31s to 5+ minutes (still climbing when killed).** Root had `^5.20260908.1`, `workers/` was first written with `^5.20260910.1` (this package publishes near-daily CalVer releases) — two different installed copies, each declaring the _entire_ Workers runtime global surface (`D1Database`, `RateLimit`, hundreds of others, plus the `Cloudflare` namespace). Running one `eslint .` across both `functions/` (root's copy) and `workers/` (its own copy) forced ESLint's shared `projectService` TS Program to reconcile two independent global-declaration universes in one process — measured, not assumed: pinning both to the identical version (`5.20260908.1`) didn't fully fix it either, so **`workers/` was given its own `eslint.config.js`** (a separate ESLint process entirely, never sharing a Program with root) and root's `lint`/`lint:fix` scripts gained `--ignore-pattern workers` (root's `eslint.config.js` itself is protected by a local hook and couldn't be edited to add an `ignores` entry — the CLI flag was the available lever). Confirmed clean afterward: `workers/` lints standalone in a few seconds, and a **local** timing check showed pristine, unmodified `main` is _also_ slow to lint on this specific sandboxed machine (Windows/Git-Bash, not Linux CI) — so "minutes" alone isn't a red flag here going forward; the real signal is the GitHub Actions run, whose historical baseline is ~31s.

**Real platform-API surprise found (F7) — the plan's "route → {perIp,
perUser} table" phrasing does not match what the binding can actually do:**

- **`@cloudflare/workers-types`' `RateLimitOptions` is `{ key: string }`
  only** — checked directly against the installed package's `index.d.ts`.
  There is no per-call `limit`/`period` override on the real, documented
  contract. (The local miniflare emulator's `RateLimiterObject` — read

  assumed — happens to also accept `limit`/`period` in its request body and

  (see below), but relying on it in `src/rateLimit.ts` itself would mean
  code that works locally and silently reverts to the binding's configured
  default the moment it runs against a real deployed binding.) So the
  numeric policy is fixed **per binding**, in `wrangler.jsonc`'s

  not a stub — `RateLimiterObject` persists `(key, period)` buckets in
  SQLite storage (`_mf_ratelimit_buckets`), keyed by

  the same F5 property D1 has: `pnpm --filter workers run validate` proves
  the rate limiter's real behavior with zero Cloudflare credentials.
- **Period is constrained to exactly `10` or `60` seconds** — the local
  emulator's `RatelimitPeriodValues = [10, 60]` and throws on anything
  else, matching the plan's own note ("the window is only 10 or 60
  seconds").
