## What already exists that 5.2 builds on (verified in the repo, not assumed from the plan)

- **D1 schema is already fully built** — migration `0001_init.sql` (landed in Phase 5.0, T2/T2a) already contains `profiles` (compressed `BLOB payload` + `payload_bytes`, per the 2026-08-31 amendment's S1) with `revision`, `schema_version`, `updated_at`. `workers/src/profileStore.ts` (T2a's boundary) already exists with the get/put/delete surface the amendment describes, gzip in the Worker via `CompressionStream`/`DecompressionStream`. **T7 does not create this table or the compression boundary — both are done.** T7 is: write the two route handlers, the optimistic-concurrency check, and the payload-cap validation on top of `profileStore.ts`.
- **`scores`/`scores_best` tables also already exist** (S3, plus migration `0002` for an ops index) — built ahead of schedule in Phase 5.0 rather than in T10/Phase 5.3 as the original plan sequenced it. Not this phase's problem, but worth knowing so nobody re-derives the DDL.
- **`workers/src/index.ts` currently registers exactly three routes**: `GET /api/health`, `POST /api/report`, `DELETE /api/account`. No `/api/profile`, no `/api/scores`, no `/api/leaderboard`, no `/api/username`, no `/api/privacy` — **confirms 5.2 has not been started**.
- **`src/auth/api.ts`** is the one fetch wrapper (T5) — `apiFetch(path, { method, token, body, timeoutMs })`, throws typed `ApiError` with a `kind` taxonomy (`network`/`timeout`/`unauthorized`/`forbidden`/`not-found`/`rate-limited`/`server`/`invalid-response`/`client`). **T8's sync engine calls this, doesn't reinvent it.**
- **`src/storage/`** is the existing local-first layer T6/T8 must not couple to structurally: `schema.ts` (`UserProfile` interface, `CURRENT_SCHEMA_VERSION = 13`), `profile.ts` (`loadProfile()`/`saveProfile(profile)` — the single write boundary, called directly by feature code like `BossPage.tsx`, no pub/sub layer exists), `attempts.ts` (`appendAttempt()`/`listAttempts()` — attempts are a **separate IndexedDB store**, not a field on `UserProfile`), `migrations.ts` (`MIGRATIONS`/`runMigrations()` — the forward-only chain T6's `blob < CURRENT` branch reuses), `exportImport.ts` (`ExportedData = { schema_version, exportedAt, profile: UserProfile, attempts: Attempt[] }` — the wire shape sync pushes/pulls; note `importData()` is a **wholesale replace** of both stores, not a merge — T6 is new logic, not an extension of anything here).
- **No pub/sub/listener layer exists in `src/storage/`** (verified — no `addEventListener`/`subscribe`/`onChange` pattern). The plan's "flows through the normal storage listeners" line doesn't correspond to a real mechanism yet in this codebase; T8 has to decide how push-after-boundary actually triggers (see the open design question in T8 below — this is new, not a wiring exercise).
- **`fast-check` is already a devDependency** (`^4.9.0`) — T6's property tests use it directly, no new dependency to add.
- **No real pre-v5 export fixture exists in the repo yet** (`find . -iname "*fixture*"` — nothing). T8's DoD explicitly requires replaying migration against "a real pre-v5 export file," not a synthetic one — getting one is a Piece 0 prep step, not a T8-time scramble.
- **`UserProfile`'s actual fields** (for the merge-rule table, from `src/storage/schema.ts`): `schema_version, rating, ratedAttemptCount, streak, requeueState, storagePersisted, dailyCompletion, rushStats, bestRunStreak, bossStats, missionProgress, missionStats, preferences, anonId, challengerName, firstRunCompleted`. Plus `attempts: Attempt[]` as a sibling in `ExportedData`, not a `UserProfile` field. This is the exhaustive list T6's `Record<keyof Profile, MergeRule>` must cover.

## New invariants for this phase

| #   | Invariant                                                                                                                                                                                                                                  | Concrete test                                                                                                                                              |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| I11 | **Merge never runs twice for the same pulled revision.** Applying the same server blob to the same local state a second time (a retried pull, a duplicate event) must be a no-op, not a double-union or a re-recompute drift               | `merge(merge(local, remote), remote) === merge(local, remote)` — idempotence test alongside T6's existing commutativity/associativity-style property tests |
| I12 | **A push never races a pull for the same local write.** The engine has exactly one in-flight direction at a time per boundary; a pull arriving mid-push (or vice versa) queues, it doesn't interleave against a half-written `UserProfile` | Concurrency test: trigger pull and push in the same tick, assert `saveProfile` is called with a fully-merged, never a partial, state                       |

These sit alongside I1–I10 unchanged — I2 (local-first lock) and I8 (SW never caches `/api/*`) are the two that bite hardest in this phase specifically, since T8 is the first task that makes real network calls on every normal play session rather than only at auth boundaries.

## T6 — merge engine, pure and alone (1 session — no I/O, no network)

**Files:** `src/sync/merge.ts`, `src/sync/merge.test.ts`, `src/sync/fixtures/` (real export files, see Piece 0-adjacent prep below).

Per-field merge rule, against the actual `UserProfile` shape verified above (write this table into the module's own doc comment, exhaustive via `Record<keyof UserProfile, MergeRule>` so a new profile field with no rule fails typecheck, not silently falls through):

| Field                                                                                                         | Rule                                                                                                                                                                                                                                                 |
| ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schema_version`                                                                                              | not merged directly — governs which branch of the skew table (below) runs; post-merge the result is stamped with the client's own `CURRENT_SCHEMA_VERSION`                                                                                           |
| `rating`                                                                                                      | **recompute**: re-derive from the merged `attempts` array via the same rating engine the client already uses for a fresh attempt, not a max/LWW pick between the two raw numbers                                                                     |
| `ratedAttemptCount`                                                                                           | **recompute**, alongside `rating` — same source, same pass                                                                                                                                                                                           |
| `streak`                                                                                                      | **recompute** from merged attempts' `localDateString`s, per the existing streak-computation logic — not max, not LWW (a stale streak can't just be the bigger number; it has to be re-derived from the actual merged activity)                       |
| `requeueState`                                                                                                | **latest `clientUpdatedAt` wins** — it's session-local scheduling state, not accumulated history                                                                                                                                                     |
| `storagePersisted`                                                                                            | **latest `clientUpdatedAt` wins** — a per-device capability flag, not something to union                                                                                                                                                             |
| `dailyCompletion`                                                                                             | **latest by date, then latest `clientUpdatedAt`** — date-scoped per its own doc comment in `schema.ts`; a stale date from either side means "not completed today," so compare dates first, only fall back to recency on a genuine same-day tie       |
| `rushStats`                                                                                                   | **non-null wins over null; else max/latest per sub-field** per the original plan's rule (bests = max, `lastRunAt` = max, counts = max — stated trade-off: counts are monotonic per device but not summable across devices without double-count risk) |
| `bestRunStreak`                                                                                               | **max**                                                                                                                                                                                                                                              |
| `bossStats`                                                                                                   | same shape as `rushStats` — non-null wins over null, else max/latest per sub-field                                                                                                                                                                   |
| `missionProgress`                                                                                             | **latest `clientUpdatedAt` wins**, non-null wins over null — an in-progress run is inherently single-device state; merging two in-progress runs field-by-field would produce a run that never happened on either device                              |
| `missionStats`                                                                                                | same shape as `rushStats`/`bossStats` — max/latest per sub-field                                                                                                                                                                                     |
| `preferences`                                                                                                 | **latest `clientUpdatedAt` wins** — true settings, last-write-wins per the original plan                                                                                                                                                             |
| `anonId`                                                                                                      | **keep local** — never overwritten by a pulled value (matches T7's server-side "first-write-wins, written once" rule; the client-side mirror of that same invariant)                                                                                 |
| `challengerName`                                                                                              | **latest `clientUpdatedAt` wins**                                                                                                                                                                                                                    |
| `firstRunCompleted`                                                                                           | **OR** (true wins) — once true on any device, it should read true everywhere; there's no legitimate path back to false                                                                                                                               |
| `attempts` (sibling of `UserProfile` in `ExportedData`, not a profile field, but part of the same merge pass) | **union by `id`**, then re-sort by `createdAt`; never drop — the union feeds the `rating`/`ratedAttemptCount`/`streak` recompute above, so this merge has to run before those, not after or in parallel                                              |
| unknown fields (older client, newer payload)                                                                  | **preserved verbatim, round-tripped** — F9; the exhaustive `Record` type only covers fields this client's `schema.ts` knows about _today_; anything else on the wire passes through untouched                                                        |

**Schema-skew policy** (unchanged from the original plan, restated because it's the part most likely to get "simplified" under deadline pressure):

| Pulled blob vs. local `CURRENT_SCHEMA_VERSION` | Action                                                                                                                                                                                                    |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `blob < CURRENT`                               | Run `src/storage/migrations.ts`'s existing `runMigrations()`/`MIGRATIONS` chain over the blob first — the same path an old IndexedDB read or an old import file already takes. No sync-specific migrator. |
| `blob === CURRENT`                             | Merge normally, per the table above.                                                                                                                                                                      |
| `blob > CURRENT`                               | **Read-only sync**: do not merge, do not push. Surface a "reload to update" notice (T8's job to wire; T6 just needs to return a distinguishable result for this branch).                                  |

**Property tests** (`fast-check`, already a devDependency): `merge(a, a) = a`; `merge(a, b) = merge(b, a)` for the union/max fields; merge never decreases an attempts count or a rating-affecting best; **new — I11's idempotence**: `merge(merge(a, b), b) = merge(a, b)`. Fixtures: one fresh-install profile, one long-lived profile, one post-mission profile — **these need to be real exports, not hand-typed objects** (get them from Thomas's own dev profile via the existing `exportData()` / Settings export button, or a throwaway test account played through a mission — either way, before this task starts, not improvised mid-task).

**DoD:** exhaustive `Record<keyof UserProfile, MergeRule>` compiles; all three skew branches tested in both directions; unknown-key round-trip test; I11 idempotence test; zero imports from `src/storage`'s IndexedDB layer (`db.ts`), `fetch`, or `@clerk/react` in `merge.ts` — it takes two `ExportedData`-shaped objects in, returns one out, nothing else.

## T7 — sync endpoints, server half (1 session)

**Files:** `workers/src/routes/profile.ts` (or inline in `index.ts` if the file stays small — match the existing convention, `report.ts` is the closest precedent), `workers/test/profile.test.ts`. No migration needed — the `profiles` table and `profileStore.ts` already exist.

`PUT /api/profile` — body `{ schemaVersion, payload, clientUpdatedAt, baseRevision, anonId? }`. Optimistic concurrency: `UPDATE profiles SET revision = revision + 1, ... WHERE clerk_user_id = ? AND revision = ?` (conditional on `baseRevision`), check `meta.changes === 1` (F10 — a statement that matches zero rows is not success), else `409` with the current server state (fetched via `profileStore.get()`). First `PUT` for a user creates the row (`revision = 1`). Payload cap: **256 KB on the decompressed JSON**, checked before `profileStore.put()` does its internal compression (per the 2026-08-31 amendment — F11's cap and S1's compression are two different layers, don't conflate them). `anonId`: written only if the column is currently null — first non-null value wins, never overwritten after.

`GET /api/profile` — `profileStore.get(userId)`, `404` if no row yet, else `{ revision, schemaVersion, payload, updatedAt }`.

Row creation for `users`: already handled by T3's lazy-insert-on-first-authenticated-write — T7 doesn't duplicate that logic, just calls into the existing `clerkAuth()` middleware and trusts `c.get('userId')` the same way `account.ts`'s `DELETE` handler already does.

**DoD:** conflict path tested (two writers racing from the same `baseRevision` — exactly one 200, one 409 with current state); a real 257 KB payload test (rejected) and a 256 KB one (accepted); authz fixture reused from T3/`account.test.ts` (user A's token can't read or write user B's profile row — this is a `WHERE clerk_user_id = ?` away from being automatic, but write the test anyway, I5 doesn't accept "obviously correct"); `anonId` first-write-wins tested (second `PUT` with a different `anonId` doesn't change the stored one); `404` on `GET` for a user with no profile row yet.

## T8 — sync orchestration, client half (1–2 sessions — the one with a real open design question)

**Files:** `src/sync/engine.ts`, `src/sync/queue.ts`, tests.

**Open design question, decided here rather than discovered mid-task:** the plan's original T8 language ("flows through the normal storage listeners") assumes a pub/sub layer over `src/storage/` that **does not exist** — `saveProfile()` is called directly by feature code (`BossPage.tsx` and siblings) with no event emitted. Two real options:

1. **Wrap `saveProfile`**: add an optional module-level subscriber list inside `src/storage/profile.ts` itself (`onProfileSaved(cb)`), fired at the end of `saveProfile()`. Minimal surface change to a locked, well-tested file — but it does mean touching `profile.ts`, which the 5.1-era convention (see `exportImport.ts`'s own doc comment: "do not modify the storage functions... if you find yourself wanting to, that's a finding to report") treats as something to be careful about, not forbidden.
2. **Call sites opt in**: every profile-mutating boundary (attempt recorded, run ended, settings changed) also calls `syncEngine.notifyMutation()` explicitly, right next to its `saveProfile()` call. No change to `src/storage/`, but it's an easy-to-miss convention — a new boundary that calls `saveProfile()` and forgets the sync hook silently drifts out of sync (no test catches a _missing_ call the way it'd catch a wrong one).

**Recommendation: option 1**, with a single grep-able test (same shape as F13's SW-denylist assertion and T2a's `payload` guard) asserting every call site that saves a profile-mutating boundary also triggers a notify — cheapest to keep honest going forward, and it's one function's internals, not new IndexedDB surface. Settle this explicitly before writing `engine.ts`; it's the one place this task can quietly turn into a game of whack-a-mole across every feature page that calls `saveProfile`.

**Behavior:**

- **Pull on boot** when signed in — non-blocking (I2): app renders from IndexedDB immediately, the pull's merge result (if any) flows through the same save path as any other local mutation.
- **Push**, debounced ~5s, after the mutation-notify hook above fires.
- **Retry queue** (`src/sync/queue.ts`): exponential backoff, capped, persisted across reload (a small IndexedDB store or `localStorage` — pick one, record why; the queue itself is disposable UI-adjacent state, not app data, so `localStorage` is defensible per the same tier `useSignupPrompt.ts` already uses), drained on the `online` event.
- **Every failure path degrades to exactly-v3 behavior silently** (I2) — a failed push doesn't block play, doesn't surface an error to the user mid-puzzle, just requeues.
- **First-sign-in migration is the ordinary flow, not a special case**: local profile + server `404` → push as revision 1; server profile + fresh device → pull then merge (T6's laws handle an empty local profile merging cleanly — verify this is actually true for the _current_ `createDefaultProfile()` shape, not assumed from the original plan's confidence). Link `anonId` on that same first push.
- **Telemetry**: `sync_push`/`sync_pull`/`sync_conflict` counts only — no payload contents (I4).

**DoD:** airplane-mode pass (I2 — signed in, offline, behaves exactly like v3); reload-with-pending-queue test; **I12** (concurrency: pull and push in the same tick don't interleave against a partial state); two real devices against the dev env, recorded in this task's own amendment; a `sync_conflict` actually provoked and observed resolving (not just unit-tested); **anonymous → account migration replayed against a real pre-v5 export file** (get one before this task starts — see the fixtures note under T6); both schema-skew branches exercised end-to-end against the dev env. **See "Verification discipline" below — the two-real-devices pass is a real manual click-through, not a scenario with an equivalent passing test.**

### Decision 1 — where `baseRevision` lives across reloads

`localStorage`, one JSON blob per device under `codoro:sync-meta`:
`{ userId, baseRevision }`. Sync metadata, not app data — same tier
`useSignupPrompt.ts` already uses for its own disposable, non-schema-versioned
local state. Read/written only by `engine.ts`; never exported/imported
alongside `exportData()`/`importData()` (it isn't part of `ExportedData` and
never should be — a revision number is meaningless on a different device).

### Decision 2 — the retry queue's persisted shape

`localStorage` under `codoro:sync-queue`, **one entry, not an array** —
`{ userId, schemaVersion, queuedAt, attempts, nextRetryAt }`. Deliberately
carries **no profile data at all**, only a marker that a push is owed: a
push, when it actually runs (whether from the 5s debounce, `flush()`, or a
drained retry), always calls `exportData()` fresh against whatever is
currently in IndexedDB — never a stale snapshot captured at the moment of
the original failure. This is why F28's schema-version check on the queue
entry is meaningful rather than vacuous: it's not "does this stale payload's
version match," it's "is the _intent_ to push still valid," because a client
update between the failed push and the drain means the ordinary
pull-then-merge cycle should re-establish sync at the new version instead of
blindly replaying old intent. `localStorage` over IndexedDB for the same
reason `useSignupPrompt.ts` chose it: this is disposable, UI-adjacent
scheduling state, not data whose loss the user would ever notice — losing a
queued retry just means the next mutation's debounce (or the next `online`
event, or the next boot's pull) re-establishes sync.

### Decision 3 — 409 handling, bounded

No change to `src/auth/api.ts`: `apiFetch`'s error path only preserves the
`{ error }` string (`errorMessageFrom`), not a conflict response's `current`
body, and extending `ApiError` to carry the full parsed body was considered
and rejected here — it would touch a locked, already-relied-upon module for
a need `engine.ts` can satisfy without it. Instead, a conflict triggers a
fresh, ordinary `GET /api/profile` (the same code path `pull()` already
runs) to fetch current server state, merge, and retry the `PUT` with the
new `baseRevision` — functionally identical to reading the 409 body, one
extra round trip, zero changes to a file outside this task's scope. Capped
at **3 total push attempts per `push()` call** (i.e. at most 2
conflict-triggered merge-and-retry cycles) — within the plan's "2–3" range,
tested exactly (`engine.test.ts`'s conflict-cap test asserts the 4th attempt
never happens and the call requeues instead of looping).

### Decision 4 — 413 is terminal, not retryable

`push()`'s per-attempt result has a distinct `too-large` kind; on it, `push()`
returns immediately without calling `enqueueRetry`/`recordQueueFailure` —
the entry never enters the queue at all. Telemetry records it as its own
`sync_push` outcome (`'too-large'`), distinguishable from a transient
network/5xx failure. Local state is untouched by construction: `push()` only
_reads_ local storage to build the outbound payload, so "leave local state
untouched" holds for every failure path, not just this one.

### F31 — account switching on one device (new footgun, promised above)

| #   | Footgun                                                                            | The mistake                                                                                                                                                                                                                                                                                                                                            | Prevented by                                                                                                                                                                                                                                                                                                                                                                                          |
| --- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F31 | **Account switching on one device carries the prior account's sync state forward** | Sync metadata (`baseRevision`) isn't keyed by user id, so signing into account B on a device that previously synced account A pushes A's stored `baseRevision` — and, if push ran before any pull, A's local profile — into B's row. The local-first IndexedDB profile does not clear on sign-out today (a separate, pre-existing, not-fixed-here gap) | `codoro:sync-meta` and `codoro:sync-queue` are both keyed by `userId`. `handleSignedIn(userId)` compares the stored `userId` to the incoming one: a mismatch discards both stores and always pulls before any push is allowed to run for the new identity (`engine.test.ts` tests both directions: same user returning keeps its meta/queue; a different user arriving discards them and pulls first) |

**Named limit, not silently papered over:** this fixes _stale-revision_ and
_push-before-pull_ corruption. It does **not** clear the local IndexedDB
profile itself on an account switch — a device that has account A's full
play history locally, then signs into account B, will still _merge_ A's
local attempts into B's server state on the first pull-then-push cycle
(`merge()` has no concept of "this attempt belongs to a different person" —
it isn't given one). That is the pre-existing gap this amendment's own
text names, not a new one T8a introduces; a real fix (clearing local state
on sign-out, or fully on sign-in-as-a-different-user) is out of this
session's file scope (`engine.ts`/`queue.ts` only) and is flagged here for
whoever picks it up next, rather than assumed solved.

  language ("`saveProfile` is called with a fully-merged, never a partial,
  state").
- **I11 (idempotence) is enforced structurally, not just tested indirectly**:
  before merging, `doPull` compares the pulled `revision` to the stored
  `baseRevision` for the current user; an exact match short-circuits to a
  `noop` result with no merge, no `appendAttempt`/`saveProfile` calls at all,
  rather than relying solely on `merge()`'s own mathematical idempotence to
  make a redundant re-application harmless.
- **Pull/push mutual exclusion (I12)** is one `async` mutex
  (`withLock`) inside `engine.ts`'s closure — every public entry point
  (`pull`, `push`, and therefore `handleSignedIn`, `notifyMutation`'s
  debounced call, `flush`, `handleOnline`) chains onto the same promise, so a
  pull and a push requested in the same tick serialize rather than
  interleave. The conflict-retry's internal re-pull calls an _unlocked_
  internal `doPull`, not the public `pull()`, to avoid a non-reentrant
  deadlock while already holding the lock from `push()`.
- **Not built this session:** any React-level wiring (a `useSyncEngine` hook,
  `main.tsx` instantiating one engine, subscribing it to `onProfileSaved`/
  `window.addEventListener('online', …)`/`visibilitychange`). The brief's
  file list is `engine.ts` + `queue.ts` + tests; the app does not yet call
  any of this in production. **T8b needs this wired before its manual pass
  can run at all** — flagged here explicitly, not discovered mid-T8b.

### Independent review (fresh context, per this task's own instruction)

A subagent with no prior context reviewed the diff cold against I1–I12,
F24–F31, and the seven required questions. It found two real bugs (both
fixed, both regression-tested) and several smaller issues. Not
self-reviewed — a controller with the intent already in its head reads code
differently than one that has to derive it, which is the whole reason this
step exists.

**B1 — `merge()`'s own documented throw path wasn't caught.** `merge.ts`'s
doc comment says a non-migratable behind-schema blob throws and "T8 catches
it like any other pull failure per I2" — `doPull` didn't. Reached via
`push()`'s conflict-retry (which calls `doPull` while already inside the
lock), this was a genuine unhandled promise rejection on `void push()`, not
just a rejected `pull()`. **Fixed**: `merge(local, remote)` wrapped in its
own try/catch, degrading to `{ kind: 'error' }` like every other pull
failure. Regression test: a schema-behind, deliberately-invalid remote
blob (mirroring the reviewer's own repro) now resolves `pull()` to
`{ kind: 'error' }` instead of rejecting.

**B2 — the local/remote timestamp comparison was structurally broken.**
`merge()`'s "latest wins" rules compare `local.exportedAt` vs
`remote.exportedAt`, but the engine built `local` fresh via `exportData()`
on every pull/push (required by Decision 2 — the queue never carries a
stale snapshot), and `exportData()` stamps `exportedAt` with "now," not
"last real mutation." Since a remote's `exportedAt` is necessarily earlier
(it was already pushed once), `local.exportedAt` was _always_ `>=` it —
every latest-wins field (`preferences`, `challengerName`, `requeueState`,
`storagePersisted`, `missionProgress`, `dailyCompletion`'s tiebreak) could
never let remote win, in either direction, ever. Verified against a real
repro before fixing, not just argued from reading the code.

**Fixed** with a persisted local-mutation clock
(`LAST_MUTATED_AT_STORAGE_KEY`, `readLastMutatedAt`/`writeLastMutatedAt` in
`engine.ts`): `notifyMutation()` stamps it (unconditionally, even
signed-out — a guest's local changes must compare correctly once they
eventually sign in); a successful merge re-stamps it to whichever side's
`exportedAt` actually won, so the _next_ comparison anchors to a real event
instead of drifting back to "whenever sync last ran." `buildLocalExportedData()`
substitutes this recorded time for `exportData()`'s own "now" stamp when
present. Two regression tests reproduce the reviewer's exact scenario in
both directions (a genuinely older recorded local clock lets remote win; a
genuinely newer one keeps local).

**Named limit on the fix, not silently claimed complete**: this only fully
closes the bug once something calls `notifyMutation()` at the real mutation
boundary — which is exactly the `onProfileSaved` → engine wiring this
session does not build (see "Not built this session," above). Until T8b
(or whoever wires it) does that, a device's very first pull/push before any
merge has ever run still falls back to "now." The regression tests call
`notifyMutation()`/seed the storage key directly, the same way the eventual
wiring will, to prove the mechanism — not to claim the gap is closed today.

**S1 — the original I12 test was vacuous.** It asserted on a 3-microtask-tick
window; `doPushOnce`'s own real IndexedDB work (`exportData()`) can't
resolve inside three microtasks regardless of whether a mutex exists, so
the test passed even with `withLock`'s body replaced by `return fn()`
(mutex fully removed) — verified directly, then reverted. **Fixed**: the
assertion window is now a genuine 200ms real delay, long enough that an
unlocked implementation's PUT would have fired on its own if nothing were
serializing it. Re-verified: disabling the mutex again now fails this
specific test (`expected … to be called 1 times, but got 2 times`),
confirmed, then the mutex was restored and diffed byte-identical to before
the experiment.

**S2 — F31's "different user arriving" test proved a weaker claim than it
looked like.** It only asserted metadata/queue were cleared; because its own
pull failed (network error), it never reached the one path where the named
limitation actually bites — a genuinely fresh account B (server 404), where
`handleSignedIn`'s ordinary "not-found → push" rule still fires and pushes
whatever local profile this device is holding (account A's, if never
cleared on sign-out) as account B's revision 1. **Added**: a test that
reaches exactly that path and asserts the pushed payload actually is
account A's data — demonstrating the named, accepted limitation directly
rather than only asserting it in prose.

**S4 — a 413 didn't clear a queue entry that already existed from an earlier,
unrelated failure.** Decision 4's "never queued" held for _creating_ an
entry but not for a pre-existing one; left in place, a device reconnecting
(`handleOnline` drains unconditionally) would repeat the same guaranteed-413
round trip forever. **Fixed**: the `too-large` branch now also calls
`clearQueue()`. Regression test added.

**N4 — `schemaSkew` wasn't cleared on sign-out**, so `getSchemaSkew()` would
keep reporting a previous account's "reload to update" state after
`handleSignedOut()`. **Fixed** (one line).

**N1 — a misbehaving `onProfileSaved` listener could turn a successful
`saveProfile()` into a rejected one** for all 20+ existing call sites.
**Fixed**: `notifyProfileSaved` now isolates each listener in its own

- N3: `SyncPushOutcome`'s `'no-token'` member is currently unreachable —
